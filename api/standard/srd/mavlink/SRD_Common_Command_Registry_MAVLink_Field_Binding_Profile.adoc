== MAVLink Binding for the Common Command Registry for Uncrewed Systems

=== Registry Commands to MAVLink Command Sequences and Field Mappings

==== Purpose

This document defines the MAVLink binding of the *Common Command Registry for Uncrewed Systems (UAV, UGV, USV, UUV)*. MAVLink is a lightweight messaging protocol commonly used for communication between uncrewed vehicles, flight controllers, onboard computers, ground stations, and other vehicle components. It complements the _A MAVLink Binding Profile for OGC API -- Routes Actions_ and makes the registry-to-MAVLink mapping explicit at *command-sequence and field level*.

The registry defines 67 protocol-neutral commands and 150 parameters. The MAVLink Routes profile defines how native MAVLink actions are represented by JSON Schema and Binding Descriptors. This document specializes that mechanism for the registry commands:

* a registry command is represented as a *composite action* whose identifier remains the registry identifier;
* the composite expands to one or more native `mavlink.*` actions, or to a gateway operation where the registry has no `MAV_CMD`;
* each carried registry parameter is mapped to a MAVLink `param1..param7`, `x/y/z`, frame, or a generated value;
* parameters for which the two source documents define no counterpart are explicitly marked *unsupported* or *unresolved*, rather than silently assigned a MAVLink meaning;
* alternatives are selected with `when` conditions as specified by REQ 43 of the MAVLink profile.

The registry remains the authority for command names, parameters, semantics, applicability and default hazards. The MAVLink profile remains authoritative for MAVLink command definitions, delivery, frames, defaults and wire representation.

The source documents identify 51 registry commands with one or more related MAVLink native actions, one composite `mission.abort`, and 15 registry commands with no `MAV_CMD` mapping. The field mappings below refine those source mappings; they do not introduce a new protocol semantic where the sources do not define one.

==== Non-goals

* Does not define new registry commands.
* Does not define autopilot-specific behavior.
* Does not define a universal mapping for vendor-specific camera, sensor or docking protocols.
* Does not turn a semantic approximation into an exact equivalence.
* Does not define continuous setpoint streams.
* Does not replace the MAVLink dialect XML; where the source documents defer to MAVLink XML, the XML is authoritative.

=== Binding conventions

==== Mapping notation

The `Field mapping` column uses the following notation:

* `registry.field → pN` -- direct mapping to MAVLink `paramN`.
* `registry.field → x/y/z` -- position or non-position wire coordinate mapping according to the MAVLink profile.
* `registry.field → geometry` -- route geometry supplies the destination/location.
* `registry.field → pN [transform]` -- a unit or value transformation is required.
* `+registry.field → generated(...)+` -- the value is not supplied by the registry command and must come from the binding/target context.
* `registry.field → unsupported` -- the source documents do not define a counterpart.
* `+registry.field → conditional(...)+` -- the mapping depends on another registry field.
* `+sequence(...)+` -- the command expands into multiple MAVLink steps.

For position-bearing commands, GeoJSON `[longitude, latitude, altitude]` is converted to MAVLink `+x=latitude×10^7+`, `+y=longitude×10^7+`, and `z=altitude` in the selected MAVLink frame. Position context is not repeated as a parameter mapping for every native step where the native action is a destination command.

==== Optional fields

An absent optional registry field requests the platform/binding default. The MAVLink profile encodes absent parameters using the dialect-defined empty value, normally `NaN` where the MAVLink definition gives NaN default/ignore semantics, otherwise `0`; a descriptor may override this with `absent`.

==== Alternatives

Where more than one native action is listed, the binding SHALL select the applicable native action with a `when` condition. Examples:

* `vehicle.hold-position`: `duration` present → `mavlink.nav-loiter-time`; otherwise → `mavlink.nav-loiter-unlim`.
* `camera.capture-image`: prefer `mavlink.image-start-capture`; legacy `mavlink.do-digicam-control` is an alternative.
* `gimbal.point`: prefer `mavlink.do-gimbal-manager-pitchyaw`; `mavlink.do-mount-control` is superseded.
* `vehicle.takeoff` and `vehicle.land`: select the ordinary or VTOL native action according to the vehicle capability.
* `payload.release`: select gripper or servo realization according to the payload implementation.

==== Delivery

`mission` means the native action can be emitted as a `MISSION_ITEM_INT`. `guided` means it is emitted through `COMMAND_INT`/`COMMAND_LONG` according to the MAVLink profile. A registry command with scope `none` is not a Routes action by default, even if a guided MAVLink command exists.

=== Composite Binding Descriptor shape

A registry action SHOULD expose a Binding Descriptor of the following form:

[,json]
----
{
  "actionId": "vehicle.goto",
  "binding": "mavlink",
  "registryVersion": "<registry version>",
  "steps": [
    {
      "kind": "mavCmd",
      "action": "mavlink.nav-waypoint",
      "delivery": ["mission"],
      "position": "geometry",
      "params": [
        { "mavParam": 1, "field": "holdTime" },
        { "mavParam": 2, "field": "acceptanceRadius" },
        { "mavParam": 4, "field": "heading" }
      ]
    }
  ],
  "unsupported": ["speed", "passThrough"]
}
----

The `action` member names a native action from the MAVLink profile. A conforming implementation may expand it directly to the underlying `MAV_CMD`, command id, delivery, frame and parameter slots.

=== Field-level implementation rules

==== Position fields

Registry `Position` parameters are context parameters when the action is attached to a Routes waypoint or segment. The MAVLink profile therefore emits them as `x/y/z` rather than `param5..param7` for destination commands. For non-destination commands with a `location` property, the Binding Descriptor uses `position: "location"`.

==== Unit conversions

The following conversions are binding operations where the native MAVLink command requires them:

|===
| Registry field | MAVLink field | Conversion

| `Position.latitude`
| `x`
| degrees → integer degrees × 10{caret}7

| `Position.longitude`
| `y`
| degrees → integer degrees × 10{caret}7

| altitude/height/depth
| `z`
| metres in selected MAVLink frame; datum/frame conversion per profile

| `vehicle.set-heading.heading`
| `CONDITION_YAW.p1`
| degrees

| `vehicle.set-heading.rate`
| `CONDITION_YAW.p2`
| deg/s

| `camera.*` time intervals
| MAVLink interval fields
| seconds remain seconds unless the native field is explicitly in µs

| `sensor.*.rate`
| `SET_MESSAGE_INTERVAL.p2`
| Hz → microseconds/message: `1,000,000 / rate`

| normalized actuator `value`
| servo PWM
| target-specific transform; not defined by the source documents
|===

==== Generated values

The following values are commonly required by the native MAVLink commands but are not registry fields:

* camera id / target camera id;
* gimbal device id;
* message id for generic sensor acquisition/status;
* mission/capture sequence counters;
* MAVLink mode enum values;
* required native parameters for `DO_SET_HOME`, calibration and reboot/shutdown where the registry has no field.

These SHALL be declared as `generated` or `fixed` in the Binding Descriptor. They SHALL NOT be silently inferred from an unrelated registry field.

==== Unsupported parameters

REQ 43 of the MAVLink profile requires a registry parameter that no native step carries to appear in `unsupported`. This is important for interoperability: the route producer can determine whether a command is fully expressible before loading it.

=== Execution and error handling

The registry's terminal outcomes are `COMPLETED`, `FAILED`, `REJECTED` and `CANCELED`. The MAVLink profile maps these from `COMMAND_ACK`, mission acknowledgements and mission progress.

For a composite registry action:

. Validate all registry parameters.
. Select native steps using `when`.
. Validate that every required registry parameter is either carried, generated by a declared binding rule, or explicitly unsupported.
. Reject a command if a required parameter is unsupported and the deployment cannot provide an alternative.
. Execute native steps in the descriptor order.
. For mission delivery, preserve route feature order as specified by the MAVLink profile.
. For guided delivery, obey target and `sequence` ordering.
. Report the native MAVLink failure/result and identify the registry field when an `INVALID_PARAMn` result can be mapped through the descriptor.

=== Conformance considerations

A registry/MAVLink implementation claiming this binding SHOULD expose, for each registry command:

* the registry `actionId`;
* the registry version;
* the selected native MAVLink command sequence;
* delivery (`mission`, `guided`);
* `param1..param7` mappings;
* `x/y/z` and frame mappings where applicable;
* unit/value transforms;
* generated/fixed values;

=== Known gaps requiring target-specific or future bindings

The source documents leave several important semantic gaps intentionally open. The most significant are:

. Generic sensor acquisition is represented through `SET_MESSAGE_INTERVAL`, but the registry does not identify a MAVLink message id for a sensor.
. Generic sensor calibration is broader than the fixed fields of `PREFLIGHT_CALIBRATION`.
. Generic docking, surfacing, emergency stop, sample collection and ranging configuration have no common `MAV_CMD` in the source mapping.
. Camera exposure and image-format configuration are outside the listed common `MAV_CMD` mapping.
. Gimbal mode semantics do not have a complete one-to-one mapping to `DO_GIMBAL_MANAGER_CONFIGURE`.
. Normalized actuator output needs a target-specific conversion to servo PWM or actuator slots.
. Underwater depth semantics are not represented by a dedicated MAVLink frame in this binding.
. Generic operating modes must be reconciled with firmware-specific custom modes.

These gaps are deliberate interoperability boundaries. An implementation may add vendor/component-specific composite steps, but those steps SHALL be clearly identified as deployment-specific rather than presented as part of this common binding.
