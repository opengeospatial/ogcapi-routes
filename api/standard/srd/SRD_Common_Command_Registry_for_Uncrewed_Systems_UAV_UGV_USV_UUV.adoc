== Common Command Registry for Uncrewed Systems (UAV, UGV, USV, UUV)

=== Vehicle Commands and Sensor Commands

==== Purpose

Uncrewed systems on air (UAV), ground (UGV), surface water (USV) and underwater (UUV) are commanded through many different vocabularies. OGC API -- Routes lets a route carry *actions* at waypoints and segments, and via its _Extensibility for Actions_ provides a mechanism to add actions without modifying the standard: a list of well-known actions, each with a properly defined schema, where `+GET /actions/{actionId}+` returns the schema or a URN or URI that points to a definition elsewhere. What is missing is the content of that list for uncrewed systems. Without shared definitions, a client cannot write "go to this position" once and have it work across vehicles.

This document defines a *Common Command Registry*: a register of well-known actions for OGC API -- Routes. It is a small, curated set of protocol-neutral command definitions that

* covers the movements and state changes common to UAV, UGV, USV and UUV (*vehicle commands*, Clause 3);
* covers the operations common to sensors and payloads carried by those vehicles (*sensor commands*, Clause 4);
* defines for each command an identifier (the Routes `actionId`), a parameter schema in SWE Common with a derived JSON Schema form for `+/actions/{actionId}+` (Clause 2.10), execution semantics, an applicability matrix by domain, and a default hazard class;
* is used as the action identifier in Routes (Clause 2.9, Clause 6.2), and can be carried by other standards: implemented by a control stream (OGC API -- Connected Systems, CS API), and mapped onto a native vehicle protocol (Annex A shows MAVLink).

The CS API can carry any command through a `ControlStream`, but it defines no shared command set. The registry gives it one without making the registry part of the CS API: the CS profile in this series maps registry actions onto control streams.

The registry contains *67 commands*: 26 vehicle commands and 41 sensor and payload commands, with 150 parameters between them. 38 commands are *Core* and 29 are *Extended*. Annex C relates the registry to the 28 well-known actions proposed in issue #74.

==== Non-goals

* Does not define a transport, a wire protocol or an autopilot behavior. It defines _what is asked_, not how a platform achieves it.
* Does not define autonomy behaviors such as collision avoidance, rules of the road, obstacle handling, or mission planning. Those are properties of the platform or of the planner.
* Does not cover swarm or multi-vehicle coordination commands, communication payload control (radios, acoustic modems) or vehicle-specific low-level control (thruster allocation, individual motor outputs).
* Does not change the Routes resources. `/actions` and `+/actions/{actionId}+` are defined by OGC API -- Routes; the registry supplies the definitions they serve.
* Does not replace vendor commands. Anything not in the registry remains available as a vendor-defined action (Clause 6.8).
* Does not define how a command is scheduled, queued or authorized. Those belong to the Routes server, to the binding in use (for example the CS API) and to the deployment.
* Does not define how a vehicle loads or executes a route, or what it does with a parameter it cannot honor. That is vehicle specific and outside OGC API -- Routes (registry Clause 2.11). The REC clauses describe a typical approach.

==== Requirements and recommendations

This document labels its statements in two ways. *REQ* marks a proposed requirement on the Routes side: what a routing server lists, serves, validates and generates. *REC* marks a recommendation for the loading side: what a component that loads a route onto a vehicle, or the vehicle itself, typically does. Loading is vehicle specific and outside OGC API -- Routes, so a REC uses SHOULD. It records the reasoning behind this document, and an implementation may depart from it. Like every SRD in this series, the document is non-binding.

=== Concepts and conventions

==== Structure of a registry entry

Each command is a Routes action and has the following members. Clauses 3 and 4 present them as a table and headline line; the companion JSON has the same names.

|===
| Member | Meaning

| `id`
| Identifier, unique within the registry (for example `vehicle.goto`)

| `uri`
| Registry URI: base URI + `id`

| `title`, `description`
| Human-readable name and one-sentence definition

| `group`
| Grouping within the clause (for example Navigation, Imaging)

| `applicability`
| For each domain UAV, UGV, USV, UUV: `applicable` (●), `limited` (○) or `not-applicable` (--)

| `level`
| `Core` (SHOULD be implemented by every system of an applicable domain that has the capability) or `Extended`

| `completion`
| When the command completes (2.4)

| `persistence`
| How long its effect lasts (2.4)

| `scope`
| Where it may appear in a route: `waypoint`, `segment`, `both`, or `none` (not a route action)

| `positionSource`
| `param` if a position parameter is filled from route geometry, otherwise `none`

| `hazard`
| Default hazard class: `none`, `flight-critical` (changes motion, mode, outputs) or `destructive` (irreversible or can disable the platform)

| `parametersSchema`
| SWE Common `DataRecord`; each field is Required (R) or Optional (O)

| `resultSchema`
| Optional schema for inline results

| `mavlink`
| Informative: related MAVLink commands
|===

==== Identifiers and URIs

Identifiers are lower-case, dot-separated, with hyphenated words. The first segment names the family:

|===
| Family | Use

| `vehicle.*`
| Commands acting on the platform (motion, state, safety)

| `mission.*`
| Commands acting on mission execution

| `sensor.*`
| Lifecycle commands valid for any sensor

| `data.*`
| Recording and annotation

| `camera.*`, `gimbal.*`, `ranging.*`, `sample.*`, `payload.*`
| Sensor and payload families
|===

In Routes the registry `id` is the `actionId`. The URI of a command is `+http://www.opengis.net/def/uxs-command/{id}+`, and it is the definition that `+GET /actions/{actionId}+` can link to (Clause 2.9). This base URI is a placeholder pending registration. Shared types have URIs under `+.../type/+`, and route-context parameters use `+http://www.opengis.net/def/routes/context/+`.

==== Domains and applicability

|===
| Symbol | Meaning

| ●
| Applicable as defined.

| ○
| Applicable with restrictions, or only for some platform types (for example `vehicle.transition` only for hybrid aircraft).

| --
| Not applicable. A system SHALL NOT declare the command for that domain without documenting its interpretation.
|===

Domains: *UAV* uncrewed aerial vehicle, *UGV* uncrewed ground vehicle, *USV* uncrewed surface vehicle, *UUV* uncrewed underwater vehicle.

==== Execution semantics

The terminal outcomes used in this document are `COMPLETED`, `FAILED`, `REJECTED` and `CANCELED`, with the meanings of the CS API `CommandStatus`. Bindings that report status in another vocabulary map them (see the MAVLink and ROS 2 bindings).

*Completion* says when the command is complete, and so reaches `COMPLETED`:

|===
| Value | Meaning

| `immediate`
| Completes once the state change has been applied (or the command has been accepted, for mode changes and settings).

| `until-goal`
| Remains `EXECUTING` until the goal is reached within tolerance, then `COMPLETED`. `FAILED` if it cannot be reached.

| `until-duration`
| `COMPLETED` when the duration has elapsed (or the time has been reached).
|===

*Persistence* says how long its effect lasts:

|===
| Value | Meaning

| `none`
| The effect ends when the command completes.

| `latched`
| A setting that stays in force for later commands until changed (for example speed, zoom). Used on a route _segment_, a latched setting is reverted at the segment end by the Routes mapping.

| `mode`
| Enters a state that persists until another command ends it (for example armed, recording, paused).

| `conditional`
| `latched` only if a parameter says so (see the command).
|===

==== Units and angles

* Units are UCUM codes (`m`, `m/s`, `deg`, `deg/s`, `s`, `Hz`, `kHz`, `dB`, `%`, `mL`, `px`, `1` for dimensionless).
* *Heading* is degrees clockwise from the reference direction (true north by default), 0 to 360.
* *Gimbal angles* with `frame = vehicle`: pitch 0 is level and positive up, yaw 0 is the vehicle's forward direction and positive clockwise. With `frame = earth`: yaw is relative to true north.
* *Time* is ISO 8601 in UTC.
* *Normalized values* are dimensionless (`1`) with a stated range.

==== Optional parameters, defaults and constraints

An optional parameter that is absent means "use the platform default". Where a description says "exactly one of" or "at least one of", the constraint applies to the group and is checked by the receiving system; a violation ends the command in `REJECTED`.

==== Registry commands as Routes actions (issue #74)

OGC API -- Routes proposes an extensibility mechanism for actions: well-known actions with a defined schema, and a response to `+GET /actions/{actionId}+` that can be a URN or a URI to a definition elsewhere. The registry is a register of such actions. A registry entry corresponds to the members that the action registry lists for a well-known action:

|===
| Routes | Registry

| Well-known action
| Command

| Short name, action id
| `id` (for example `vehicle.land`)

| Action name
| `title`

| Definition
| `description`

| Applicability
| `applicability` by domain (2.3)

| Duration unit
| A `duration` parameter in `s`, where the command has a duration (`vehicle.hold-position`, `vehicle.orbit`, `mission.wait`). Other commands end as their `completion` value says (2.4)

| Schema
| `parametersSchema` (2.10)

| URN or URI of a definition elsewhere
| `uri` (2.2)
|===

A Routes server uses the registry as follows (Clause 6.2):

. It lists the commands it supports in `GET /actions`, with the registry `id`.
. `+GET /actions/{actionId}+` returns the schema, or a link to the registry URI.
. A route carries the action in `actions[]` with `actionType` set to the registry `id`.

Actions that are not in the registry are added in the same way, with a vendor identifier (Clause 6.8), and need no change to the Routes standard.

==== Schema forms

The registry defines parameters in SWE Common, the form the CS API serves at `+/controlstreams/{id}/schema+`. A Routes server MAY serve the same definition as JSON Schema, which is the form used for `+GET /actions/{actionId}+` (issue #72). The derivation is:

|===
| SWE Common | JSON Schema

| `DataRecord`
| `object`, with `properties` from its fields and `required` listing the fields marked R

| `DataArray`
| `array`, with `items` from the element type

| `Quantity`
| `number`, with `minimum` and `maximum` from the interval constraint, and the UCUM unit in `x-ucum`

| `Count`
| `integer`, with the same constraints

| `Boolean`
| `boolean`

| `Category`
| `string`, with `enum` from the allowed values

| `Text`
| `string`

| `Time`
| `string` with `format: date-time`

| Default value
| `default`

| `definition` URI of a component
| `x-definition`

| Shared type (2.5)
| A `$ref` to the type URI
|===

This derivation is proposed (Clause 9, question 14). Clause 7.1 shows the result for `vehicle.goto`.

==== Loading a route (informative)

A routing server generates a plan. It does not need to know which vehicle will execute it, so `target` is optional in an `actions[]` entry. A vehicle characteristics model (maximum altitude, maximum depth, transit speed, and which optional capabilities the vehicle supports) is an optional input to generation, used to plan sensibly. When a route is loaded onto a vehicle, targets that were not given are resolved, and the route is translated into the vehicle's own commands. How that is done is vehicle specific and outside OGC API -- Routes. The bindings of this series describe a typical approach as recommendations.

A typical loader treats the parameters of an action as follows:

* If the binding has a counterpart and the vehicle's characteristics allow it, the parameter is carried, after any conversion.
* If the binding has no counterpart, or the vehicle's characteristics do not declare the capability, an optional parameter is dropped and a warning is reported.
* A required parameter that cannot be carried makes the action unloadable.

A warning names the action (`actionType`), its `sequence`, the parameter, and a reason: `no-counterpart` or `not-declared`. The warning format and the characteristics model are not defined here.

=== Requirements and recommendations

==== Registry entries

*REQ R1* -- A registry entry SHALL have the members of Clause 2.1, and its `parametersSchema` SHALL be a SWE Common component tree that can be converted to JSON Schema by Clause 2.10. It SHALL also be valid for the CS API Command Schema (`parametersSchema` member).

*REQ R2* -- Identifiers SHALL be unique and immutable. A command that is withdrawn SHALL be marked `deprecated` and its identifier SHALL NOT be reused.

==== Routes actions

*REQ R3* -- Listing. A Routes server that supports a registry command SHALL list it in `GET /actions` with `id` equal to the registry `id` (for example `vehicle.land`), and SHOULD give the registry URI as its definition. A server MAY also accept the short names of Annex C (for example `land`) as aliases, and SHALL then return the registry `id` in every response.

*REQ R4* -- Definition. `+GET /actions/{actionId}+` for a registry command SHALL return either (a) the parameter schema of the command in one of the forms of Clause 2.10, or (b) a link, as a URI or URN, to the registry definition of the command (issue #74). A server SHOULD return form (a), because a client can then validate an action without a second request.

*REQ R5* -- Schema content. The schema served for a registry command SHALL contain every parameter of the command, with the registry name, component type, unit and default. A server given a vehicle characteristics model MAY use it to bound values while it generates a route (for example a maximum altitude), and SHALL NOT remove registry parameters from the schema because of it. A binding profile MAY add parameters to a command (Clause 6.8). An added parameter SHALL be optional, SHALL have a default, and SHALL be named with the profile name as a prefix (`mavlink.rate`). A route that omits an optional parameter uses its default.

*REQ R6* -- Action instances. An `actions[]` entry whose `actionType` is a registry `id` SHALL carry `params` that validate against the schema served for the action, and SHALL appear only where the `scope` of the command allows it (Clause 2.1). A command with scope `none` is not a route action. Context parameters (Clause 2.5) are filled from the route geometry and are not set by the route author. The entry MAY omit `target`, because a routing server does not need to know the vehicle. When it is omitted, the target is resolved when the route is loaded, or is given by a mapping supplied with the generation request. How a vehicle loads a route, including what it does with a parameter it cannot honor, is vehicle specific and outside OGC API -- Routes (Clause 2.11).

==== Control streams (CS API binding)

These recommendations apply where a registry command is implemented by a CS API control stream, which is one binding of a registry action. They concern the vehicle side. The CS profile in this series describes how a loader matches actions to such streams.

*REC R7* -- A control stream that implements a registry command SHOULD declare it with the members:

[,json]
----
"commandType": "http://www.opengis.net/def/uxs-command/vehicle.goto",
"commandOptions": ["speed", "acceptanceRadius", "holdTime"]
----

`commandType` is the registry URI. `commandOptions` lists the optional registry parameters that the stream supports. (Both members are proposed extensions to the CS API `ControlStream` resource.)

*REC R8* -- The control stream's `parametersSchema` SHOULD contain every *required* registry parameter with the registry name, component type and unit. It MAY narrow constraints (intervals, values) to platform limits. It MAY contain additional optional parameters whose names begin with `x-`.

*REC R9* -- A control stream SHOULD implement every parameter listed in `commandOptions`. A command carrying a parameter that the stream does not implement is handled as Clause 2.11 describes: the parameter is dropped with a warning, or the command ends in `REJECTED` with an explanatory `message`. Which of the two is vehicle specific.

==== Units and positions

*REQ R10* -- Units SHALL be as in Clause 2.7. A vehicle that uses other internal units SHOULD convert; the schema SHALL state the registry unit.

*REQ R11* -- Positions SHALL use WGS 84 latitude and longitude in degrees. A vehicle SHOULD support the vertical references marked ● for its domain in Clause 2.6 that its sensors allow, and SHOULD treat a position whose `verticalReference` it cannot use as unsupported (Clause 2.11). A vehicle SHOULD NOT reinterpret one vertical reference as another without an exact conversion.

==== Execution

*REC R12* -- A command SHOULD follow the `completion` value in its entry (Clause 2.4). A command with `until-goal` completion SHOULD report progress through `EXECUTING` status reports where the platform can, and SHOULD end in `FAILED` with a `message` if the goal cannot be reached.

*REC R13* -- Movement supersession. A new movement command (`vehicle.goto`, `follow-path`, `orbit`, `move-relative`, `return-to-home`, `hold-position`, `stop`, `takeoff`, `land`, `surface`, `dock`) for a System replaces a movement command still in progress for that System. The replaced command SHOULD end in a terminal state, `CANCELED` with a `message` naming the replacing command, unless the platform processes commands strictly in order (queueing), in which case it does not replace.

*REC R14* -- Persistence. The effect of a `latched` or `mode` command SHOULD last until it is changed by another command or by a platform reset. A system SHOULD document what happens at the end of a mission and after a restart.

==== Safety

*REQ R15* -- Hazard classes in the registry are *minimum* classes. A deployment MAY raise a command's class, and SHALL NOT lower a `destructive` command. A `vehicle.set-armed` command with `force = true` SHALL be treated as `destructive`. `sensor.set-power` and `sensor.calibrate` SHALL be classed at least `flight-critical` for sensors the vehicle depends on for navigation or control.

*REQ R16* -- Route safety. A `destructive` command SHALL NOT be issued as part of an automatically executed route sequence. It requires an explicit, separately authorized request.

==== Results, applicability and versioning

*REC R17* -- Results. A command with a result SHOULD provide the `resultSchema` given in its entry for inline results, and, where the binding is the CS API, SHOULD report produced observations and data streams as `CommandResult` links.

*REC R18* -- A system declaring a registry command for a domain marked -- in its entry SHOULD document its interpretation. Declaring an Extended command is optional; when declared, it SHOULD conform to this document.

*REQ R19* -- Versioning. The registry SHALL carry a version (major.minor.patch). Adding commands or optional parameters is a minor change. Removing a command, or changing the meaning, type, unit or requiredness of a parameter, is a major change. A Routes server and a control stream SHOULD state the registry version they implement.

=== Extension and governance

* *Vendor commands.* Identifiers begin with `+x-{vendor}.+`, for example `x-acme.deploy-net`. They have no registry URI and are not covered by this document. A Routes server lists them in `/actions` like any other action, and `+GET /actions/{actionId}+` returns their schema or a link to the vendor's own definition (issue #74). The Routes standard does not change.
* *Profile parameters.* A binding profile (MAVLink, ROS 2, ...) may add optional parameters to a registry command. Their names begin with the profile name (`mavlink.rate`, `ros2.timeAllowance`), and each has a default, so a route that omits it is valid (REQ R5). The profile describes them and serves them in the schema; they are not part of the registry entry. A parameter that several profiles add can be proposed for the registry.
* *Proposing a command.* A proposal contains the entry members of Clause 2.1, the applicability matrix, at least two independent implementations (or one implementation and a written mapping to a native protocol), and an example. Additions are minor versions (REQ R19).
* *Deprecation.* A deprecated command remains in the registry for at least one major version and names its replacement.
* *Hosting.* The registry is expected to live on an OGC-hosted register (a definitions server), one URI per command, with the JSON form and this document as human-readable views.
