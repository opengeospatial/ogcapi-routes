== A ROS 2 Binding for the Common Command Registry for Uncrewed Systems

=== Carrying Registry Commands over ROS 2 Actions, Services and Topics

Companion files: `uxs-ros2-binding.json` (machine-readable Binding Descriptors for every registry command) and `uxs_interfaces.tar.gz` (proposed ROS 2 interface package, Tier 3)._

==== Purpose

ROS 2 (Robot Operating System 2) is an open-source, component-based middleware for robot software development. It provides a language-neutral publish--subscribe and request--reply communication model over DDS, with concepts such as nodes, topics, services, actions and parameters. ROS 2 is transport-agnostic and supports real-time, multi-robot and security-hardened deployments through SROS2 and DDS security.

The Common Command Registry defines 67 protocol-neutral commands for UAV, UGV, USV and UUV vehicles and their sensors. This document specifies how each registry command is carried over ROS 2: which existing service, action or topic realizes it, how parameters and results are converted, and how the execution state is reported. It was written by surveying the ROS 2 interface definitions themselves, not by assuming what exists (Clause 1.2).

The binding has three tiers, because ROS 2 has no complete command vocabulary for uncrewed systems:

|===
| Tier | Source | Used for

| *1*
| Standard and widely deployed ROS 2 packages: Nav2 (`nav2_msgs`), `std_srvs`, `lifecycle_msgs`, `rcl_interfaces`, `diagnostic_msgs`, `control_msgs`, `rosbag2_interfaces`, `geographic_msgs`
| Ground and surface navigation, generic sensor lifecycle, grippers, recording

| *2*
| Autopilot bridges: MAVROS (`mavros_msgs`) and PX4 uXRCE-DDS (`px4_msgs`)
| Aerial commands, gimbals, camera triggers, mode and arming, MAVLink-based surface and underwater vehicles

| *3*
| A proposed package `uxs_interfaces`, generated from the registry
| Every command that neither tier covers, and a uniform alternative for all others
|===

Of the 67 registry commands, 57 have at least one Tier 1 or Tier 2 interface, and 10 have none and can only be carried by Tier 3 (Clause 1.2). The Tier 3 package has 67 interface definitions generated from the registry (25 actions, 42 services, 2 shared messages).

==== Non-goals

* Does not define a ROS 2 transport, DDS configuration or discovery beyond what ROS 2 provides.
* Does not define how a vehicle loads or executes a route, or what it does with a parameter it cannot honor. That is vehicle specific and outside OGC API -- Routes (registry Clause 2.11). The REC clauses describe a typical approach.
* Does not define low-level control (velocity commands, thruster or joint trajectories). `cmd_vel` and trajectory controllers are outside the registry.
* Does not replace the registry or the MAVLink profile. MAVROS and PX4 are bridges to MAVLink and PX4, and the MAVLink mapping stays authoritative for what a `MAV_CMD` means.
* Does not define perception, SLAM, map or localization interfaces, except where a command needs a coordinate conversion (Clause 4.3).

==== Requirements and recommendations

This document labels its statements in two ways. *REQ* marks a proposed requirement on the Routes side: what a routing server lists, serves, validates and generates. *REC* marks a recommendation for the loading side: what a component that loads a route onto a vehicle, or the vehicle itself, typically does. Loading is vehicle specific and outside OGC API -- Routes, so a REC uses SHOULD. It records the reasoning behind this document, and an implementation may depart from it. Like every SRD in this series, the document is non-binding. Every statement in this document is a REC.

=== Requirements and recommendations

==== Tiers and the Binding Descriptor

*REC 1* -- Every registry command SHOULD have at most one *active* binding per System, chosen from the list in its Binding Descriptor. The control stream's `commandOptions` (registry REC R7) SHOULD list only the parameters that the active interface can carry. A parameter the interface cannot carry SHOULD NOT be listed.

*REC 2* -- A Binding Descriptor entry has the members:

[,json]
----
{
  "tier": 1,
  "package": "nav2_msgs",
  "interface": "NavigateToPose",
  "kind": "action",
  "name": "navigate_to_pose",
  "fit": "partial",
  "parameterMap": "location → pose (PoseStamped, frame map); heading → pose.orientation",
  "conversions": "lat/lon → map frame with robot_localization /fromLL; ENU yaw = π/2 − heading",
  "notes": "speed, acceptanceRadius, holdTime, passThrough are not goal fields."
}
----

`kind` is `action`, `service` or `topic`. `name` is relative to the System namespace unless it starts with `/`. `fit` is `exact` (all registry parameters carried), `partial` (some optional parameters cannot be carried), or `generic` (a transport that can carry any MAVLink command, used for one command).

*REC 3* -- Partial fit. When the active interface cannot carry an optional parameter, a gateway SHOULD drop it and report a warning (registry Clause 2.11). Whether it rejects the command instead (registry REC R9) is vehicle specific. A required parameter that the interface cannot carry makes the command unloadable.

*REC 4* -- Generic MAVLink transports (`mavros_msgs/CommandLong`, `CommandInt`, `px4_msgs/VehicleCommand`) SHOULD be used only with the MAVLink command given in the registry mapping for that command (registry Annex A). A gateway SHOULD NOT expose arbitrary command numbers.

==== Naming and discovery

*REC 5* -- A System SHOULD correspond to a ROS 2 namespace. The System description SHOULD carry that namespace as an identifier (`ros2:namespace`), and, for multi-domain systems, the DDS domain id (`ros2:domain`).

*REC 6* -- Tier 1 and Tier 2 interfaces SHOULD be used under the names given in the descriptor, relative to the System namespace (for example `/rover1/navigate_to_pose`). Tier 3 interfaces SHOULD be named `+uxs/{family}/{command}+` with hyphens replaced by underscores (for example `/rover1/uxs/camera/capture_image`).

*REC 7* -- Discovery. A gateway SHOULD determine the supported commands of a System from the ROS graph: it lists action and service names and types in the System's namespace and matches them with the descriptor by *type and name*. A name match with a different type SHOULD be ignored. The gateway builds the control streams (with `commandType` and `commandOptions`) from the matches.

*REC 8* -- Options. For a Tier 3 interface, the node SHOULD declare a string-array parameter `+uxs.options.{command}+` listing the supported optional parameters. Where it is absent, the gateway assumes that only required parameters are supported.

==== Conventions: units, frames, geodesy

*REC 9* -- Units. ROS 2 follows REP 103 (SI units, angles in radians). Registry angles are in degrees. Conversions SHOULD be as declared in the descriptor. Tier 2 interfaces that pass values through to MAVLink keep the MAVLink units (for example the `GimbalManagerPitchyaw` service takes degrees and deg/s).

*REC 10* -- Headings. A registry heading is degrees clockwise from true north. REP 103 yaw is positive counter-clockwise about the up axis, with 0 along east in ENU frames. The conversion is

----
yaw_ENU(rad) = π/2 − heading(deg) · π/180,   wrapped to (−π, π]
----

For `reference = magnetic-north`, the gateway applies the local declination first. For `reference = relative`, the gateway adds the heading to the current yaw taken from TF. Nav2's `Spin` takes a *relative* rotation: the gateway computes `wrap(target yaw − current yaw)`.

*REC 11* -- Geodetic positions. Nav2 goals are poses in a local frame (normally `map`). To convert a registry `Position`, a gateway SHOULD use the `robot_localization` service `/fromLL` (request `ll_point` of type `geographic_msgs/GeoPoint`, response `map_point` of type `geometry_msgs/Point`), which requires the `navsat_transform_node` to be running. `FollowGPSWaypoints` accepts `GeoPose` directly and performs the same conversion itself. Where no conversion service is available, the command SHOULD be rejected.

*REC 12* -- Vertical reference. Nav2 is planar: for ground vehicles the `vertical` and `verticalReference` of a position are ignored. For MAVROS and PX4, `verticalReference` maps to the MAVLink frame (`msl` → `MAV_FRAME_GLOBAL`, `home` → `MAV_FRAME_GLOBAL_RELATIVE_ALT`, `terrain` → `MAV_FRAME_GLOBAL_TERRAIN_ALT`). `ellipsoid` has no MAVLink frame and requires a geoid conversion (registry and MAVLink profile). `depth` and `seabed` have no ROS 2 or MAVLink frame and require a vendor convention, for example a negative relative altitude.

*REC 13* -- Precision. `mavros_msgs` services `CommandTOL` and `CommandHome`, and `GimbalManagerSetRoi`, carry latitude, longitude and altitude as `float32`. A `float32` near 45° has a resolution of about 4 × 10⁻⁶ degrees (about 0.4 m), and larger values up to about 0.9 m. A gateway SHOULD use `CommandInt` (int32 degE7 coordinates) where metre-level accuracy matters, and SHOULD declare the resolution of any binding that uses `float32`.

==== Tier 3: generated interface conventions

*REC 14 (e)* -- Tier 3 interfaces SHOULD be generated from the registry entry, with one interface per command: an *action* for `until-goal` and `until-duration` commands, a *service* for `immediate` commands. The package is `uxs_interfaces`; interface names are the camel-cased identifier (`vehicle.set-heading` → `VehicleSetHeading`).

*REC 15 (e)* -- Type mapping:

|===
| Registry type | ROS 2 type | Unset value (optional parameter)

| Quantity
| `float64`
| `NaN`

| Count (required, ≥ 0)
| `uint32`
| --

| Count (optional or signed)
| `int32`
| `-1`

| Boolean (required)
| `bool`
| --

| Boolean (optional)
| `uint8` with `+{NAME}_FALSE = 0+`, `+{NAME}_TRUE = 1+`, `+{NAME}_UNSET = 255+`
| `255`

| Category
| `uint8` with constants `+{NAME}_{VALUE}+` numbered from 0 in registry order
| `+{NAME}_UNSET = 255+`

| Text
| `string`
| empty string

| Time
| `builtin_interfaces/Time`
| zero

| Position, VerticalTarget
| `uxs_interfaces/Position`, `uxs_interfaces/VerticalTarget` (optional: companion `+bool has_{name}+`)
| `+has_{name} = false+`

| Position[]
| `uxs_interfaces/Position[]`
| empty array
|===

Field names are the registry names in snake_case. Angles are in radians and all other units are the registry unit, documented in the field comment.

*REC 16 (e)* -- Every Tier 3 result or response SHOULD contain `bool success`, `uint16 error_code` with the constants `ERROR_NONE` (0), `ERROR_UNSUPPORTED_PARAMETER` (1), `ERROR_INVALID_VALUE` (2), `ERROR_PRECONDITION_FAILED` (3), `ERROR_TIMEOUT` (4), `ERROR_HARDWARE_FAULT` (5), `ERROR_UNKNOWN` (99), and `string message`, followed by the result fields of the registry entry. Every Tier 3 action feedback SHOULD contain `float32 progress` (0 to 1, NaN if unknown) and `builtin_interfaces/Duration elapsed`.

*REC 17 (e)* -- A Tier 3 server SHOULD reject (goal rejected, or `success = false` with `ERROR_UNSUPPORTED_PARAMETER`) a request that sets an optional parameter it does not list in `+uxs.options.{command}+` (REC 8).

==== Execution mapping

*REC 18 (d)* -- Completion. A command implemented by an action is `until-goal` or `until-duration` and reaches `COMPLETED` when the action result reports success. A command implemented by a service is `immediate` and is `COMPLETED` when the response reports success. A `topic` binding has no acknowledgment: a gateway SHOULD report it `COMPLETED` on publication and SHOULD mark the status as unconfirmed.

*REC 19 (d)* -- Status mapping:

|===
| ROS 2 signal | CS API `CommandStatus` | Notes

| Goal rejected by the action server
| `REJECTED`
|

| `GoalStatus.STATUS_ACCEPTED` (1)
| `ACCEPTED`
|

| `STATUS_EXECUTING` (2)
| `EXECUTING`
| `percentCompletion` from feedback where possible

| `STATUS_CANCELING` (3)
| `EXECUTING`
| Cancellation requested

| `STATUS_SUCCEEDED` (4)
| `COMPLETED`
|

| `STATUS_CANCELED` (5)
| `CANCELED`
|

| `STATUS_ABORTED` (6)
| `FAILED`
| `message` from the result `error_msg`

| Service response `success = false` (or a MAVROS `result` of a failure code)
| `FAILED`
|

| Service not available within the timeout
| `REJECTED`
| Reason `server unavailable`

| Action server or service not found
| `REJECTED`
|

| Result or response not received within the timeout
| `FAILED`
| Reason `timeout`
|===

*REC 20 (d)* -- Progress. Where the action feedback provides a progress measure, a gateway SHOULD map it to `percentCompletion`. For Nav2 `NavigateToPose` and `NavigateThroughPoses`, progress is derived from `distance_remaining` against the initial distance. Nav2 error codes (for example `TF_ERROR`, `TIMEOUT`) SHOULD be carried in the status `message`.

*REC 21 (d)* -- Supersession and cancellation. A new movement goal sent to an action server that supports one active goal can preempt the previous goal, which then ends `STATUS_ABORTED` or `STATUS_CANCELED`. The gateway SHOULD report such a goal as `CANCELED` with a `message` naming the replacing command. Explicit cancellation uses `action_msgs/srv/CancelGoal`; to stop all goals on a server, the request has a zero goal id and a zero timestamp.

==== Live binding

*REC 22 (c)* -- A class (c) gateway SHOULD use one ROS 2 client per bound interface, wait for the server within a configured timeout (default 5 s) before sending, and apply a result timeout per command. It SHOULD NOT send a goal to a lifecycle node that is not in the `active` state (`lifecycle_msgs/GetState`).

*REC 23 (c)* -- Concurrency. A gateway SHOULD send at most one in-flight goal to an action server that supports one active goal, in `sequence` order (Routes), unless the registry `pipeline` option permits otherwise.

*REC 24 (c)* -- Time. A gateway and the robot SHOULD use consistent time sources. When `use_sim_time` is true on the robot, the gateway SHOULD stamp headers in simulation time.

*REC 25 (c)* -- Multi-robot. Every System SHOULD have its own namespace (REC 5). Gateways SHOULD NOT use absolute interface names shared by several Systems, and SHOULD respect the DDS domain declared in the System description.

==== Safety and security

*REC 26* -- Hazard. The hazard class of the registry entry applies to the ROS 2 binding. A `destructive` command (for example a forced disarm, reboot, or flight termination through `CommandLong`) SHOULD require separate authorization and SHOULD NOT be issued from an automatically executed route (registry REQ R16). A gateway SHOULD NOT bind a `destructive` command to a `topic`.

*REC 27* -- Security. Production deployments SHOULD use SROS2 (DDS security) or an equivalent, so that only authenticated nodes can call command interfaces. A gateway SHOULD authenticate clients of its own API and SHOULD NOT forward a command on behalf of an unauthenticated client.

==== Composite and non-route commands

*REC 28 (d)* -- `mission.abort`. The registry command `mission.abort` (`Completion: immediate`, `Persistence: mode`, `Scope: none`, `Hazard: flight-critical`) has one required parameter, `action`, with the values `hold`, `return-to-home`, `land`, `surface` and `stop`. A gateway SHOULD perform it as follows:

. Resolve the fallback first. The fallback is the registry command of the same name (`hold` → `vehicle.hold-position`, `return-to-home` → `vehicle.return-to-home`, `land` → `vehicle.land`, `surface` → `vehicle.surface`, `stop` → `vehicle.stop`) with default parameters, through its active binding (REC 1). If no binding can carry it, the gateway SHOULD end `mission.abort` as `REJECTED` with a `message`, and SHOULD NOT have sent any cancellation.
. Cancel every active goal that the gateway has on the movement action servers of the System, using `action_msgs/srv/CancelGoal` with a zero goal id and a zero timestamp (REC 21). The cancelled goals end as `CANCELED` with a `message` naming `mission.abort`.
. Send the fallback, unless it is `stop`: the cancellation in step 2 already is the registry binding of `vehicle.stop` for Nav2 (Annex B), and a second request SHOULD NOT be sent.
. Report `mission.abort` as `COMPLETED` when the cancellation has been accepted and the fallback has been accepted by its server (action goal accepted, or service `success = true`). The progress of a fallback that is an action (for example `return-to-home`) is not part of `mission.abort`. If the cancellation or the fallback fails, `mission.abort` is `FAILED` with the cause in `message`.

The gateway SHOULD stop sending the remaining Commands of the aborted route to that System.

*REC 29 (c)* -- Commands outside a route. A registry command whose scope is `none` (for example `mission.start`, `mission.pause`, `mission.abort`, `vehicle.set-armed`, `vehicle.reboot`) is not a route action. A gateway SHOULD execute it only on an explicit, authenticated request (REC 27), and SHOULD NOT issue it as a step of a route sequence (registry REQ R16). Its status is reported as in REC 18--19.

=== Worked example

*Scenario:* the survey route from the earlier profiles, executed by a ground rover `rover1` (Nav2, GPS localization) carrying a camera `camera1`. Three waypoints. Waypoints 1 and 2 capture a photo, waypoint 3 holds for ten seconds.

==== Discovery

The gateway lists the graph in the `/rover1` namespace:

|===
| ROS 2 name | Type | Matched registry command | Tier

| `/rover1/navigate_to_pose`
| `nav2_msgs/action/NavigateToPose`
| `vehicle.goto` (partial)
| 1

| `/rover1/follow_gps_waypoints`
| `nav2_msgs/action/FollowGPSWaypoints`
| `vehicle.follow-path` (partial)
| 1

| `/rover1/wait`
| `nav2_msgs/action/Wait`
| `vehicle.hold-position`, `mission.wait` (partial)
| 1

| `/rover1/spin`
| `nav2_msgs/action/Spin`
| `vehicle.set-heading` (partial)
| 1

| `/rover1/camera1/uxs/camera/capture_image`
| `uxs_interfaces/action/CameraCaptureImage`
| `camera.capture-image`
| 3
|===

Active bindings: `vehicle.goto` → `NavigateToPose`, `mission.wait` → `Wait`, `camera.capture-image` → Tier 3. The derived `commandOptions` for `vehicle.goto` is `["heading"]`: `NavigateToPose` carries a pose (position and orientation), so `heading` can be carried, while `speed`, `acceptanceRadius`, `holdTime` and `passThrough` are not listed (REC 1, 3).

==== Mapping a route

|===
| # | Action | Interface | Converted request

| 1
| `vehicle.goto` (waypoint 1)
| `/rover1/navigate_to_pose`
| `pose.header.frame_id = map`; `pose.position` from `/fromLL` (lon 7.63, lat 45.02); orientation unset (identity)

| 2
| `camera.capture-image`
| `/rover1/camera1/uxs/camera/capture_image`
| `count = 1`, `interval = NaN`

| 3
| `vehicle.goto` (waypoint 2)
| `/rover1/navigate_to_pose`
| position from `/fromLL` (lon 7.64, lat 45.03)

| 4
| `camera.capture-image`
| as row 2
| `count = 1`

| 5
| `vehicle.goto` (waypoint 3)
| `/rover1/navigate_to_pose`
| position from `/fromLL` (lon 7.65, lat 45.04)

| 6
| `mission.wait`
| `/rover1/wait`
| `time = 10 s`
|===

The gateway sends one goal at a time, waits for `STATUS_SUCCEEDED` (mapped to `COMPLETED`) and then sends the next. The hold at waypoint 3 is `mission.wait` (registry scope `waypoint`), not a plugin of the waypoint follower (Clause 1.2, finding 5).

==== Execution feedback

While goal 1 runs, the `NavigateToPose` feedback (`distance_remaining`, `estimated_time_remaining`) provides `percentCompletion`. If the planner gives up, the result carries a Nav2 error code and `error_msg`; the gateway reports `FAILED` with that text and applies the route's `onFailure` policy.

==== The same route on a UAV

For `drone7` flying through MAVROS, the same registry commands map differently:

|===
| Registry command | Interface | Note

| `vehicle.takeoff`
| `mavros_msgs/srv/CommandTOL` at `cmd/takeoff`
| `altitude`, `latitude`, `longitude` are `float32` (REC 13)

| `vehicle.goto`
| `mavros_msgs/srv/CommandInt` at `cmd/command_int`, `DO_REPOSITION` (192)
| degE7 coordinates, `speed` → param 1

| `camera.capture-image`
| `mavros_msgs/srv/CommandLong` at `cmd/command`, `IMAGE_START_CAPTURE` (2000)
| generic transport

| `vehicle.land`
| `mavros_msgs/srv/CommandTOL` at `cmd/land`
| `descentRate` unsupported

| `vehicle.set-armed`
| `mavros_msgs/srv/CommandBool` at `cmd/arming`
| `force` unsupported
|===

MAVROS services return a `success` flag and a MAVLink `result` byte; the gateway maps them by REC 19. Because `DO_REPOSITION` returns when the command is acknowledged and not when the position is reached, the gateway SHALL detect arrival from position telemetry (`global_position/global`) to report `COMPLETED`.

==== What a class (a)+(b) client does

. Reads the interface catalog (Annex B) once and caches it with the registry version.
. Checks which parameters each bound interface can carry, and drops the others with a warning (REC 3).
. Converts parameters (REC 9--13) with no ROS graph, for example a heading to an ENU yaw.

==== What a class (c)--(d) client additionally does

. Lists the graph in the System namespace and matches names and types (REC 7).
. Sends one goal at a time, in sequence order, once the server is available and any lifecycle node is `active` (REC 22--23).
. Maps `GoalStatus` and feedback to `CommandStatus` and `percentCompletion` (REC 19--20), and reports a preempted goal as `CANCELED` (REC 21).

==== Abandoning the mission with `mission.abort`

`mission.abort` ("Abandon the mission and perform a fallback action") is a Core command with `Completion: immediate`, `Persistence: mode`, `Scope: none` and `Hazard: flight-critical`. It is not a route action (REC 29). Two cases show how it differs between vehicles.

*Rover `rover1` with `action = stop`.* Goal 5 of the route (`NavigateToPose`) is `EXECUTING`. An authorized operator sends `mission.abort` with `{"action": "stop"}`.

|===
| Step | Interface | Result

| 1. Resolve the fallback
| `vehicle.stop` → `action_msgs/srv/CancelGoal` (Tier 1)
| Available (REC 28, step 1)

| 2. Cancel
| `CancelGoal` on `/rover1/navigate_to_pose/_action/cancel_goal`, goal id zero, stamp zero
| Goal ends `STATUS_CANCELED`, reported as `CANCELED` with a `message` naming `mission.abort`

| 3. Fallback
| none: the cancellation is the binding of `vehicle.stop`
| No second request

| 4. Report
| `CancelGoal` response accepted
| `mission.abort` is `COMPLETED`
|===

The gateway sends no further Commands of the route (row 6 of Clause 5.2, the hold at waypoint 3).

*Drone `drone7` with `action = return-to-home`.* MAVROS has no action servers, so step 2 has nothing to cancel. The gateway resolves `vehicle.return-to-home` to `mavros_msgs/srv/CommandLong` at `cmd/command` with `NAV_RETURN_TO_LAUNCH` (20) (Annex B, Tier 2, `generic`). The `finalAction` and `vertical` parameters of the registry command are not set by `mission.abort`, so nothing is dropped (REC 3). The call returns `success = true`, which the gateway maps to `COMPLETED` for `mission.abort` (REC 19). The aircraft's flight home is then a separate matter, observed through telemetry. The same `action = surface` would be `REJECTED` for `drone7`, because `vehicle.surface` has no Tier 1 or Tier 2 interface, unless the System offers the Tier 3 interface `uxs/vehicle/surface` (REC 28, step 1).

=== Implementation notes

These are notes on the ROS 2 packages surveyed in Clause 1.2, not requirements, and they change between distributions. Verify against the target distribution.

|===
| Topic | Note

| Distribution differences
| Interfaces were extracted from development branches. Some of them (for example `DockRobot`, `UndockRobot`, `FollowObject`) may not exist, or may have different fields, in older distributions. Check the target distribution.

| Action names
| The Nav2 action names used here (`navigate_to_pose`, `navigate_through_poses`, `follow_path`, `follow_waypoints`, `follow_gps_waypoints`, `spin`, `backup`, `drive_on_heading`, `wait`, `dock_robot`, `undock_robot`) appear as string literals in the Nav2 sources, but deployments remap them.

| Waypoint task executors
| `WaitAtWaypoint`, `PhotoAtWaypoint`, `InputAtWaypoint` are plugins configured by parameters; they cannot express per-waypoint commands.

| GPS conversion
| `FollowGPSWaypoints` calls `/fromLL` for each GPS pose and skips or aborts when the conversion fails, depending on its `stop_on_failure` parameter.

| MAVROS
| Most services are under `mavros/cmd/*`, `mavros/mission/*`, and (extras) `mavros/gimbal_control/*`; the prefix depends on the node name and namespace. `SetMode` and `set_message_interval` are at the plugin root.

| PX4
| `px4_msgs` messages are used through the uXRCE-DDS agent (`/fmu/in/*`, `/fmu/out/*`). The `VehicleCommand` message has over 100 command constants in this snapshot, and the acknowledgment arrives on `VehicleCommandAck`.

| Lifecycle
| Sensor drivers that are lifecycle nodes publish only when active, so `sensor.start-acquisition` is an `ACTIVATE` transition, and `sensor.stop-acquisition` a `DEACTIVATE`.

| Quality of service
| Services and actions use the default reliable QoS. Topic bindings (`speed_limit`) should use reliable QoS to match the subscriber.

| Not compiled
| The `uxs_interfaces` files were linted for syntax (types, names, sections) but not built with `rosidl`.

==== Binding details

`fit`: *exact* carries all registry parameters, *partial* cannot carry some optional parameters (REC 3), *generic* is a MAVLink escape hatch (REC 4). `+{action}+` and `+{node}+` stand for the name of the action server or node concerned.

|===
| Command | Tier | Interface | ROS name | Fit | Parameter mapping | Conversions | Notes

| `vehicle.goto`
| 1
| `nav2_msgs` action `NavigateToPose`
| `navigate_to_pose`
| partial
| `location` → `pose` (PoseStamped, frame `map`); `heading` → `pose.orientation`
| lat/lon → map frame with `robot_localization` service `/fromLL` (`GeoPoint` → `Point`); ENU yaw = π/2 − heading (rad), wrapped to (−π, π]; quaternion about z
| `speed`, `acceptanceRadius`, `holdTime`, `passThrough` are not goal fields (controller and goal-checker parameters). Commands carrying them are rejected.

| `vehicle.goto`
| 1

| `follow_gps_waypoints`
| partial

| Nav2 converts lat/lon itself through `/fromLL`; ENU yaw = π/2 − heading (rad), wrapped to (−π, π]; quaternion about z
| Single-element list. Same unsupported parameters as above.

| `vehicle.goto`
| 2
| `mavros_msgs` service `CommandInt`
