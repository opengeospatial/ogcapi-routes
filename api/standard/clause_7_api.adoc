[[routing-api]]
== Routing API

=== Overview

This clause specifies the API building blocks for a Web API for Routing based on the <<OGCWebAPIGuidelines,OGC Web API Guidelines>>, <<CommonCore,OGC API Common>> and the <<REM,OGC Route Exchange Model>>. The API building blocks are specified in the following requirements/conformance classes:

* Minimal routing capability:
** **Core**: Routing based on start/end point.
* Additional API capabilities:
** **Manage routes**: Store, fetch and delete routes stored on the server.
* Additional routing parameters:
** **Mode**: Specify the type of transport when computing the route.
** **Intermediate waypoints**: Pass through additional points along the route.
** **Spatial constraints**: Specify spatial constrains and restrictions, optionally also with a time-based constraint.

The API building blocks support the resources and operations listed in <<tldr>>.

[#tldr,reftext='{table-caption} {counter:table-num}']
.Overview of resources and applicable HTTP methods and media types
[cols="16,20,10,18,18,18",options="header"]
!===
|Resource |Path |HTTP method |Request media type |Response media type |Document reference
|Landing page |`/` |GET |n/a |`application/json` |<<landing_page>>
|Conformance declaration |`/conformance` |GET |n/a |`application/json` |<<conformance_declaration>>
.2+|Routes .2+|`/routes` |POST |`application/json` |`application/geo+json` |<<compute_route>>
|GET |n/a |`application/json` |<<get_routes>>
.2+|Route .2+|`/routes/{routeId}` |GET |n/a |`application/geo+json` |<<get_route>>
|DELETE |n/a |n/a |<<delete_route>>
|Route definition |`/routes/{routeId} /definition` |GET |n/a |`application/json` |<<get_route_definition>>
|Modes |`/modes` |GET |n/a |`application/json` |<<get_list_of_modes>>
|Mode |`/modes/{modeId}` |GET |n/a |`application/json` |<<get_mode_schema>>

The first three operations are available in the 'Core' requirements class.  All routing
APIs implementing this Standard will support them. The following five operations are implemented by routing APIs implementing the
'Manage routes' requirements class.

[[geometries]]
==== Geometries

All implementations of this Standard will support geometries encoded as GeoJSON. This includes the waypoints in the route definition and the geometries of all features in the route exchange model (overview, start, end, segments).

All geometries use coordinates based on the World Geodetic System 1984 (WGS 84) datum, i.e., the coordinate reference system (CRS) used by Global Positioning System (GPS). In GeoJSON, a coordinate is an array of numbers. The first two elements are longitude and latitude, or easting and northing, precisely in that order and specified in decimal numbers. Ellipsoidal height may be included as an optional third element.

Support for additional encodings or additional CRSs may be specified in future extensions.

[[routes]]
==== Routes

[[compute_route]]
===== Compute a new route

This operation creates a new route. The payload of the request specifies the definition of the new route.

The core requirements class supports a minimum route definition by using two `waypoints`: The start and end point of the route.

In addition, clients can select a routing `mode` among those offered by the server. The API declares the modes that it supports in the `Modes` API resource.

An optional `name` for the route can be provided. The name can be used as the title in links to the route and the name is also included in the route itself.

[[req_core_compute-route-op]]
[width="90%",cols="2,6a"]
|===
^|*Requirement {counter:req-id}* |*/req/core/compute-route-op*
^|A |The server SHALL support the HTTP POST operation at the path `/routes`.
^|B |The server SHALL accept a route definition in the content of the request based upon the following OpenAPI 3.0 schema:

[source,YAML]
----
type: object
required:
  - inputs
properties:
  inputs:
    type: object
    required:
      - waypoints
    properties:
      name:
        type: string
      waypoints:
        type: object
        required:
          - value
        properties:
          value:
            type: object
            required:
              - type
              - coordinates
            properties:
              type:
                type: string
                enum:
                  - MultiPoint
              coordinates:
                title: Points along the route
                type: array
                minItems: 2
                items:
                  type: array
                  minItems: 2
                  maxItems: 2
                  items:
                    type: number
      mode:
        type: string
----
|===

Additional members in the route definition can be ignored.

NOTE: The content model of the route definition object has been designed so that it can also be the content of a process execution request according to the OGC API - Processes - Part 1: Core Standard. The motivation for this is the following: The computation of a route is a process that operates on geospatial data that typically includes a routing dataset, which is a networked dataset that has a set of connected vertices and edges that have topological properties on which analysis can be done. This standard specifies the OGC API building blocks for Routes as API resources. An alternate implementation option for a routing API could be to implement routing as a Process resource using the building blocks specified in the OGC API - Processes - Part 1: Core Standard. The current design allows that the same request can be sent to both API options to compute a new route. 
The decision to align the payload with OGC API Processes adds additional members "inputs" and "value" that would otherwise be unnecessary.

[[get_routes]]
===== Fetch routes

This operation returns a list of routes that are currently available.

To support access to servers with many stored routes without overloading the client, the API supports paged access with links to the next page, if more routes are available than the page size. The `limit` parameter can be used to control the subset of the routes that will be returned in the response, the page size. Each page can include information about the number of routes available to the client and the number of routes returned in the response (`numberMatched` and `numberReturned`) as well as links to support paging (link relation `next`). This approach is aligned with the paging of the Features resource in <<OGCAPIFeatures,OGC API - Features - Part 1: Core>>.

[width="90%",cols="2,6a"]
|===
^|*Requirement {counter:req-id}* |*/req/manage-routes/get-routes-success*
^|A |A successful execution of the operation SHALL be reported as a response with a HTTP status code `200`.
^|B |The content of that response SHALL be based upon the following OpenAPI 3.0 schema:

[source,YAML]

type: object
properties:
  numberMatched:
    type: integer
    minimum: 0
    description: The total number of routes available to the client on the server
      (across all pages).
  numberReturned:
    type: integer
    minimum: 0

    type: array

      type: object

          type: string

          type: string
        type:

[[req_manage-routes_get-routes-limit]]
[width="90%",cols="2,6a"]
|===
^|*Requirement {counter:req-id}* |*/req/manage-routes/get-routes-limit*
^|A |For the HTTP GET operation at the path `/routes`, the server SHALL support a query parameter `limit` based upon the following OpenAPI 3.0 schema:

[source,YAML]
----
name: limit
in: query
description: The maximum number of routes to return in the response.
  If the value is larger than the maximum supported by the server,
  the maximum value is used instead.
required: false
schema:
  type: integer
  minimum: 1
  default: 100
  example: 100
style: form
explode: false
----
^|B |If the server does not return all routes available to the client in the response, the response SHALL include a link with link relation type `next` that conforms to the schema in `/req/manage-routes/get-routes-success` B.
^|C |The URI of the `next` link SHALL refer to the same resource (path `/routes`) and, when dereferenced, SHALL return the next page of routes, that is, the routes that immediately follow the routes in the response that included the `next` link.
|===

NOTE: Servers are free in how they implement the `next` link. Two common approaches from <<OGCAPIFeatures,OGC API - Features>> apply here as well: opaque continuation links that are managed by the server (clients have to be prepared to receive a `404` response for expired links), or links that add an implementation-specific query parameter to `/routes`, for example an `offset` parameter (as in `GET /routes?limit=50&offset=50`).

NOTE: Clients cannot assume that paging is safe against changes to the routes stored on the server while a client iterates through `next` links. If a server provides opaque links these could be safe and maintain the state during the original request. Using a parameter for the start index, however, will not be safe. Additional requirements classes for safe paging can be added in extensions to this specification.

[[req_manage-routes_get-route-success]]
[width="90%",cols="2,6a"]

[[delete_route]]
===== Delete a route

This operation deletes a route with identifier `routeId`.
If the route is still in processing, the routing process is canceled.
[[req_manage-routes_delete-route-op]]
[width="90%",cols="2,6a"]
|===
^|*Requirement {counter:req-id}* |*/req/manage-routes/delete-route-op*
^|A |The server SHALL support the HTTP DELETE operation at the path `/routes/{routeId}` for each route referenced from the Routes resource at `/routes`.
|===

[[req_manage-routes_delete-route-success]]
[width="90%",cols="2,6a"]
|===
^|*Requirement {counter:req-id}* |*/req/manage-routes/delete-route-success*
^|A |A successful execution of the operation SHALL be reported as a response with a HTTP status code `200` with a status document in the response body.
^|B |The status document SHALL include at least the following properties:
** `routeId`: a unique identifier for the route
** `type`: SHALL be "route"
** `status`: SHALL be "dismissed"
** `message`: a human-readable message describing the result
** `created`: the timestamp when the route calculation was created (ISO 8601)
** `started`: the timestamp when the route calculation started (ISO 8601, optional)
** `finished`: the timestamp when the route calculation finished (ISO 8601, optional)
^|C |The server SHALL respond with HTTP status code `404` if the route does not exist.
^|D |The server SHALL respond with HTTP status code `500` if an unexpected server failure occurs.
|===

The behavior depends on the state of the route:
[#tldr,reftext='{table-caption} {counter:table-num}']
.DELETE Behaviour
[options="header"]
|===
|Situation |Behavior |Response
|Calculation accepted or running |The server cancels the calculation, releases its resources, and dismisses the job. |200 OK with status document (application/json)
|Calculation complete (route exists) |The server deletes the stored route. |200 OK with status document (application/json)
|Route does not exist (unknown, already deleted, or expired) |Nothing to delete. |404 Not Found with problem details (RFC 9457)
|Unexpected server failure |The server encounters an unexpected error. |500 Internal Server Error with problem details (RFC 9457)
|===

After a successful DELETE, a GET request to `/routes/{routeId}` returns `404 Not Found`.
A repeated DELETE on the same route returns `404 Not Found`.

[[rec_mode_domain-names]]

** **Definition**: The area of the Earth's surface, including its terrain, cities, and infrastructure.
** **Scope**: The domain extends from the surface of the Earth to the high-water mark.
** **Overlaps**: The Ground Domain overlaps with the Maritime Domain in the landward segment of the littorals (coastal areas).
* **Maritime Domain**
** **Definition**: The oceans, seas, bays, rivers, lakes, estuaries and coastal areas of the Earth.
** **Scope**: The Domain includes the surface, subsurface (underwater).
* **Air Domain**
** **Definition**: The atmosphere, beginning at the Earth's surface and extending upwards.
** **Scope**: The Domain extends to the altitude where atmospheric effects become negligible. This is often considered to be the Kármán line (100 km) or the edge of "near space" (around 70,000 feet, or roughly 20 km).

|Dependency |<<OGCAPIProcesses,OGC API - Processes - Part 1: Core>>
|===

[[req_job_control_async]]
[width="90%",cols="2,6a"]
|===
^|*Requirement {counter:req-id}* |*/req/job-control/async*

A client MAY request asynchronous execution of a route computation by sending a HTTP POST request to `/routes` with the header `Prefer: respond-async` (RFC 7240).

The server response depends on whether the server supports asynchronous execution for the requested mode:

* If the server supports asynchronous execution for the mode:
  - The server SHALL respond with status code `201 Created`
  - The response SHALL include a `Location` header with the route ID
  - The response SHALL include a `Preference-Applied: respond-async` header
  - The response body SHALL be a status document with at least the following properties:
    - `routeId`: a unique identifier for the route computation
    - `type`: SHALL be "route"
    - `status`: the current status of the computation (one of: "accepted", "running", "successful", "failed", "dismissed")

* If the server does not support asynchronous execution for the mode:
  - The server SHALL respond with status code `400 Bad Request`
  - The response body SHALL be a problem details document (RFC 9457) explaining that asynchronous execution is not supported

|===

[[req_job_control_status]]
[width="90%",cols="2,6a"]
|===
^|*Requirement {counter:req-id}* |*/req/job-control/status*

The server SHALL support the HTTP GET operation at the path `/routes/{routeId}` to retrieve the status of a route computation.

The response depends on the status of the computation:

|Situation |Response
|Calculation in progress (status is "accepted" or "running") |200 OK with status document (application/json)
|Calculation complete (status is "successful") |200 OK with the route (application/geo+json)
|Route does not exist |404 Not Found with problem details (RFC 9457)
|Valid request, but no route can be computed |422 Unprocessable Entity with problem details (RFC 9457)
|Unexpected server failure |500 Internal Server Error with problem details (RFC 9457)
|===

[[req_job_control_modes]]
[width="90%",cols="2,6a"]
|===
^|*Requirement {counter:req-id}* |*/req/job-control/modes*

Each mode supported by the server SHALL include a `jobControlOptions` property in the response from `/modes` and `/modes/{modeId}`.

The `jobControlOptions` property is an array of strings that indicates which execution modes are supported for the route computation. Valid values are:
* `sync-execute`: Synchronous execution is supported (default if property is omitted)
* `async-execute`: Asynchronous execution is supported
