[[routing-api]]
== Routing API

=== Overview

This clause specifies the API building blocks for a Web API for Routing based on the <<OGCWebAPIGuidelines,OGC Web API Guidelines>>, <<CommonCore,OGC API Common>> and the <<REM,OGC Route Exchange Model>>. The API building blocks are specified in the following requirements/conformance classes:

* Minimal routing capability:
** **Core**: Routing based on start/end point.
* Additional API capabilities:
** **Manage routes**: Store, fetch and delete routes stored on the server.
* Additional routing parameters:
** **Mode**: Specify the type of transport when computing the route.
** **Intermediate waypoints**: Pass through additional points along the route.
** **Spatial constraints**: Specify spatial constrains and restrictions, optionally also with a time-based constraint.

The API building blocks support the resources and operations listed in <<tldr>>.

[#tldr,reftext='{table-caption} {counter:table-num}']
.Overview of resources and applicable HTTP methods and media types
[cols="16,20,10,18,18,18",options="header"]

|Conformance declaration |`/conformance` |GET |n/a |`application/json` |<<conformance_declaration>>
.2+|Routes .2+|`/routes` |POST |`application/json` |`application/geo+json` |<<compute_route>>
|GET |n/a |`application/json` |<<get_routes>>
.2+|Route .2+|`/routes/{routeId}` |GET |n/a |`application/geo+json` |<<get_route>>
|DELETE |n/a |n/a |<<delete_route>>

The first three operations are available in the 'Core' requirements class.  All routing
APIs implementing this Standard will support them. The following five operations are implemented by routing APIs implementing the
'Manage routes' requirements class.

[[geometries]]
==== Geometries

All implementations of this Standard will support geometries encoded as GeoJSON. This includes the waypoints in the route definition and the geometries of all features in the route exchange model (overview, start, end, segments).

All geometries use coordinates based on the World Geodetic System 1984 (WGS 84) datum, i.e., the coordinate reference system (CRS) used by Global Positioning System (GPS). In GeoJSON, a coordinate is an array of numbers. The first two elements are longitude and latitude, or easting and northing, precisely in that order and specified in decimal numbers. Ellipsoidal height may be included as an optional third element.

Support for additional encodings or additional CRSs may be specified in future extensions.

[[routes]]
==== Routes

[[compute_route]]
===== Compute a new route

This operation creates a new route. The payload of the request specifies the definition of the new route.

The core requirements class supports a minimum route definition by using two `waypoints`: The start and end point of the route.

In addition, clients can select a routing `mode` among those offered by the server. The API declares the modes that it supports in the `Modes` API resource.

An optional `name` for the route can be provided. The name can be used as the title in links to the route and the name is also included in the route itself.

[[req_core_compute-route-op]]
[width="90%",cols="2,6a"]
|===
^|*Requirement {counter:req-id}* |*/req/core/compute-route-op*
^|A |The server SHALL support the HTTP POST operation at the path `/routes`.
^|B |The server SHALL accept a route definition in the content of the request based upon the following OpenAPI 3.0 schema:

[source,YAML]
----
type: object
required:
  - inputs
properties:
  inputs:
    type: object
    required:
      - waypoints
    properties:
      name:
        type: string
      waypoints:
        type: object
        required:
          - value
        properties:
          value:
            type: object
            required:
              - type
              - coordinates
            properties:
              type:
                type: string
                enum:
                  - MultiPoint
              coordinates:
                title: Points along the route
                type: array
                minItems: 2
                items:
                  type: array
                  minItems: 2
                  maxItems: 2
                  items:
                    type: number
      mode:
        oneOf:
          - type: string
          - type: object
            required:
              - value
            properties:
              value:
                type: object
                required:
                  - id
                properties:
                  id:
                    type: string
----
|===

Additional members in the route definition can be ignored.

NOTE: The route definition is limited to the inputs of the route computation: an optional `name`, the `waypoints`, an optional `mode`, and optional spatial and temporal constraints. Actions and contingencies are not members of the route definition. They are created by the server and appear only in the route representation returned by the server, which is based on the <<REM,OGC Route Exchange Model>> (see <<rc_actions>> and <<rc_contingencies>>).

NOTE: The route definition object is also a valid process execution request according to the <<OGCAPIProcesses,OGC API - Processes - Part 1: Core>> Standard, so the same payload can be sent either to this API or to a generic OGC API - Processes implementation that exposes routing as a process. This alignment is the only reason the payload includes the "inputs" member and the "value" members, which would otherwise be unnecessary; see <<alignment-processes,Alignment with OGC API - Processes>>.

[[get_routes]]
===== Fetch routes

This operation returns a list of routes that are currently available.

To support access to servers with many stored routes without overloading the client, the API supports paged access with links to the next page, if more routes are available than the page size. The `limit` parameter can be used to control the subset of the routes that will be returned in the response, the page size. Each page can include information about the number of routes available to the client and the number of routes returned in the response (`numberMatched` and `numberReturned`) as well as links to support paging (link relation `next`). This approach is aligned with the paging of the Features resource in <<OGCAPIFeatures,OGC API - Features - Part 1: Core>>.

[[req_manage-routes_get-routes-success]]
[width="90%",cols="2,6a"]
|===
^|*Requirement {counter:req-id}* |*/req/manage-routes/get-routes-success*
^|A |A successful execution of the operation SHALL be reported as a response with a HTTP status code `200`.
^|B |The content of that response SHALL be based upon the following OpenAPI 3.0 schema:

[source,YAML]
----
type: object
properties:
  numberMatched:
    type: integer
    minimum: 0
    description: The total number of routes available to the client on the server
      (across all pages).
  numberReturned:
    type: integer
    minimum: 0
    description: The number of links with link relation type "item" in this response.
  links:
    type: array
    items:
      type: object
      required:
        - rel
        - href
      properties:
        href:
          type: string
        rel:
          type: string
        type:
          type: string
        hreflang:
          type: string
        title:
          type: string
----
^|C |The links SHALL include a link (link relation `item`) to a route currently on the server.
^|D |If a route has a name, the name SHALL be used in the link title.

Access to this resource will typically require authentication. The server will only include links 
to routes that the client is authorized to access.

[[req_manage-routes_get-routes-limit]]
[width="90%",cols="2,6a"]
|===
^|*Requirement {counter:req-id}* |*/req/manage-routes/get-routes-limit*
^|A |For the HTTP GET operation at the path `/routes`, the server SHALL support a query parameter `limit` based upon the following OpenAPI 3.0 schema:

[source,YAML]
----
name: limit
in: query
description: The maximum number of routes to return in the response.
  If the value is larger than the maximum supported by the server,
  the maximum value is used instead.
required: false
schema:
  type: integer
  minimum: 1
  default: 100
  example: 100
style: form
explode: false
----
^|B |If the server does not return all routes available to the client in the response, the response SHALL include a link with link relation type `next` that conforms to the schema in `/req/manage-routes/get-routes-success` B.
^|C |The URI of the `next` link SHALL refer to the same resource (path `/routes`) and, when dereferenced, SHALL return the next page of routes, that is, the routes that immediately follow the routes in the response that included the `next` link.
|===

NOTE: Servers are free in how they implement the `next` link. Two common approaches from <<OGCAPIFeatures,OGC API - Features>> apply here as well: opaque continuation links that are managed by the server (clients have to be prepared to receive a `404` response for expired links), or links that add an implementation-specific query parameter to `/routes`, for example an `offset` parameter (as in `GET /routes?limit=50&offset=50`).

NOTE: Clients cannot assume that paging is safe against changes to the routes stored on the server while a client iterates through `next` links. If a server provides opaque links these could be safe and maintain the state during the original request. Using a parameter for the start index, however, will not be safe. Additional requirements classes for safe paging can be added in extensions to this specification.

[[delete_route]]
===== Delete a route

This operation deletes a route with identifier `routeId`.
If the route is still in processing, the routing process is canceled.
[[req_manage-routes_delete-route-op]]
[width="90%",cols="2,6a"]
|===
^|*Requirement {counter:req-id}* |*/req/manage-routes/delete-route-op*
^|A |The server SHALL support the HTTP DELETE operation at the path `/routes/{routeId}` for each route referenced from the Routes resource at `/routes`.
|===

[[req_manage-routes_delete-route-success]]
[width="90%",cols="2,6a"]
|===
^|*Requirement {counter:req-id}* |*/req/manage-routes/delete-route-success*
^|A |A successful execution of the operation SHALL be reported as a response with a HTTP status code `200` with a status document in the response body.
^|B |The status document SHALL include at least the following properties:
** `routeId`: a unique identifier for the route
** `type`: SHALL be "route"
** `status`: SHALL be "dismissed"
** `message`: a human-readable message describing the result
** `created`: the timestamp when the route calculation was created (ISO 8601)
** `started`: the timestamp when the route calculation started (ISO 8601, optional)
** `finished`: the timestamp when the route calculation finished (ISO 8601, optional)
^|C |The server SHALL respond with HTTP status code `404` if the route does not exist.
^|D |The server SHALL respond with HTTP status code `500` if an unexpected server failure occurs.
|===

The behavior depends on the state of the route:
[#tldr-delete,reftext='{table-caption} {counter:table-num}']
.DELETE Behaviour
[options="header"]
|===
|Situation |Behavior |Response
|Calculation accepted or running |The server cancels the calculation, releases its resources, and dismisses the job. |200 OK with status document (application/json)
|Calculation complete (route exists) |The server deletes the stored route. |200 OK with status document (application/json)
|Route does not exist (unknown, already deleted, or expired) |Nothing to delete. |404 Not Found with problem details (RFC 9457)
|Unexpected server failure |The server encounters an unexpected error. |500 Internal Server Error with problem details (RFC 9457)
|===

After a successful DELETE, a GET request to `/routes/{routeId}` returns `404 Not Found`.
A repeated DELETE on the same route returns `404 Not Found`.

[[rc_modes]]
=== Requirements Class "Modes"

Modes is a restriction based on the route operation or type of transport desired when computing the route. For instance, "drone", "truck-shortest" or "public-fastest". The API declares the modes that it supports. Each mode can have its own specific schema, allowing clients to define parameters for the mode when creating a new route.

[cols="1,4",width="90%"]
|===
2+|*Requirements Class*
2+|http://www.opengis.net/spec/ogcapi-routes-1/1.0.0-draft.2/req/modes

|Dependency |<<rc_core>>
|===

[[req_mode_input]]
[width="90%",cols="2,6a"]
|===
^|*Requirement {counter:req-id}* |*/req/mode/input*
^|A |The server SHALL support a member at the JSON Pointer `/inputs/mode` in the route definition in a HTTP POST request to the path `/routes` based on the following schema:

[source,YAML]
----
oneOf:
  - type: string
  - type: object
    required:
      - value
    properties:
      value:
        type: object
        required:
          - id
        properties:
          id:
            type: string
----
^|B |In the object form, the `id` member of the `value` member SHALL match the `id` of a mode listed in the Modes resource at `/modes`. A string value is a shorthand for the object form `{ "value": { "id": <string> } }`.
^|C |Members of the `value` member other than `id` are mode-specific parameters. [[rec_mode_domain-names]]
[width="90%",cols="2,6a"]
|===
^|*Recommendation {counter:rec-id}* |*/rec/core/domain-names*
^|A |The domain names SHOULD be selected from the following list:

* **Ground Domain**
** **Definition**: The area of the Earth's surface, including its terrain, cities, and infrastructure.
** **Scope**: The domain extends from the surface of the Earth to the high-water mark.
** **Overlaps**: The Ground Domain overlaps with the Maritime Domain in the landward segment of the littorals (coastal areas).
* **Maritime Domain**
** **Definition**: The oceans, seas, bays, rivers, lakes, estuaries and coastal areas of the Earth.
** **Scope**: The Domain includes the surface, subsurface (underwater).
* **Air Domain**
** **Definition**: The atmosphere, beginning at the Earth's surface and extending upwards.
** **Scope**: The Domain extends to the altitude where atmospheric effects become negligible. This is often considered to be the Kármán line (100 km) or the edge of "near space" (around 70,000 feet, or roughly 20 km).
|===

===== Actions in the route representation

Action instances are created by the server (see <<rc_actions>>) and appear in the route representation returned by the server. They are encoded as objects with an `actionType` member that identifies the action, a `params` member with the action parameters, and optional `id`, `description`, `target` and `sequence` members. Depending on when they are executed, action instances appear:

* in the `actions` member of the route feature collection (executed when the route starts, and their reverts when the route ends);
* in the `actions` member of the `properties` of a `start`, `segment` or `end` feature (executed at that position);
* in the `segment_actions` member of the `properties` of a `segment` feature (executed along the stretch that ends at the segment's position).

[[req_actions_encoding]]
[width="90%",cols="2,6a"]
|===
^|*Requirement {counter:req-id}* |*/req/actions/encoding*
^|A |An action instance in a route representation SHALL include an `actionType` member whose value is the identifier of an action listed in the Actions resource at `/actions`.
^|B |An action instance SHALL include a `params` member. The value of `params` SHALL validate against the schema served for the action at `/actions/{actionId}`.
^|C |An action instance MAY include an `id` member with an identifier for the instance, a `description` member with human-readable text, a `target` member with a URI that identifies the vehicle, sensor, camera, gimbal or payload the action is executed on, and a `sequence` member with a number that orders the action among the actions of the same target.
|===

=== Requirements Class "Attributes"

The Attributes requirements class defines a discoverable catalog of attributes that a Routes API may include in the representation of any route component. It separates the definition of an attribute from the values returned for a particular route component.

An attribute is identified by a stable `attributeId`. Attribute definitions
declare the parts of a route to which they apply, their value type, and, where
relevant, their unit of measure or permitted categorical values.

[cols="1,4",width="90%"]
|===
2+|*Requirements Class*
2+|http://www.opengis.net/spec/ogcapi-routes-1/1.0.0-draft.2/req/attributes

|Dependency |<<rc_core>>

[[req_attributes_catalog]]
[width="90%",cols="2,6a"]
|===
^|*Requirement {counter:req-id}* |*/req/attributes/catalog*

^|B |A successful execution of the operation SHALL be reported with HTTP status code `200`.

[[attributes_in_routes]]
==== Use in route representations

Attribute values are returned as entries in the `attributes` array of the applicable route component. Each entry references an attribute defined in the global catalog through its `attributeId` and supplies the value for that particular route component.

For example, if `segLength`, `surface`, `segType`, `segDur`, `risk`, and `segEnergy` are declared in the attribute catalog, a route segment may include:

[source,JSON]
----
{
  "type": "Feature",
  "geometry": {
    "type": "LineString",
    "coordinates": []
  },
  "properties": {
    "segId": "d4f6b2e0-83a5-4f81-9d37-4d7f5f5a9c21",
    "attributes": [
      {
        "attributeId": "segLength",
        "value": 1240.5
      },
      {
        "attributeId": "surface",
        "value": "paved"
      },
      {
        "attributeId": "segType",
        "value": "turn"
      },
      {
        "attributeId": "segDur",
        "value": 312
      },
      {
        "attributeId": "risk",
        "value": "medium"
      },
      {
        "attributeId": "segEnergy",
        "value": {
          "amount": 185.4,
          "unit": "Wh"
        }
      }
    ]
  }
}
----

The `attributeId` values reference definitions published at `/attributes`; the route segment representation does not redefine their schemas. An empty `attributes` array indicates that no attributes are populated for that route component.

Attribute definitions are published through a global catalog at `/attributes` and can be retrieved individually at `/attributes/{attributeId}``. Each definition declares the route components to which it may apply. Modes may reference supported attribute identifiers, but do not redefine their schemas. An empty attributes array indicates that no attributes are populated for that mode.

[[rc_contingencies]]
=== Requirements Class "Contingencies"

This requirements class specifies how a server declares the contingencies that it supports. Like actions, contingencies are **not** part of the route definition sent by the client. The server associates contingencies with the computed route, and they are executed when their trigger conditions occur during the traversal of the route.

[cols="1,4",width="90%"]
|===
2+|*Requirements Class*
2+|http://www.opengis.net/spec/ogcapi-routes-1/1.0.0-draft.2/req/contingencies
|Target type |Web API
|Dependency |<<rc_core>>
|===

[[contingencies]]
==== Contingencies

[[fetch_contingencies]]
===== Fetch the list of contingencies

This operation fetches the list of available contingencies offered by the server.

[[req_core_compute-list-contingencies]]
[width="90%",cols="2,6a"]
|===
^|*Requirement {counter:req-id}* |*/req/core/list-contingencies*
^|A |The server SHALL support the HTTP GET operation at the path `/contingencies`.
^|B |The content of that response SHALL be based upon the following OpenAPI 3.0 schema::

[source,YAML]

type: array
items:
  type: string
----
^|C |The server SHALL support the HTTP GET operation at the path `/contingencies/{contingencyId}` for each available contingency.

===== Contingencies in the route representation

[[req_contingencies_encoding]]
[width="90%",cols="2,6a"]
|===
^|*Requirement {counter:req-id}* |*/req/contingencies/encoding*

^|B |A contingency instance MAY include a `timeout_s` member with the number of seconds the condition must hold before the contingency is executed.

This requirement enable the API request to specify the time of departure or arrival. The default value is an immediate departure.

[cols="1,4",width="90%"]
|===
2+|*Requirements Class*

[[req_time_input]]
[width="90%",cols="2,6a"]
|===
^|*Requirement {counter:req-id}* |*/req/time/input*
^|A |The server SHALL support a member at the JSON Pointer `/inputs/temporal_constraint` in the route definition in a HTTP POST request to the path `/routes` based on the following schema (a time constraint object):

[source,YAML]
----
type: object
required:
  - value
properties:
  value:
    type: object

      - id
      - title
      - timePoint
      - type

        type: string

[[rc_job-control]]
=== Requirements Class "Job Control"

This requirement class enables the API to support asynchronous execution of route computation requests using the same execution model as OGC API - Processes.

[cols="1,4",width="90%"]
|===
2+|*Requirements Class*
2+|http://www.opengis.net/spec/ogcapi-routes-1/1.0.0-draft.2/req/job-control
|Target type |Web API
|Dependency |<<rc_core>>
|Dependency |<<OGCAPIProcesses,OGC API - Processes - Part 1: Core>>
|===

[[req_job-control_async]]
[width="90%",cols="2,6a"]
|===
^|*Requirement {counter:req-id}* |*/req/job-control/async*
^|A |A client MAY request asynchronous execution of a route computation by sending a HTTP POST request to `/routes` with the header `Prefer: respond-async` (RFC 7240).
^|B |If the server supports asynchronous execution for the requested mode:

** The server SHALL respond with status code `201 Created`.
** The response SHALL include a `Location` header with the URI of the new route computation, which is a direct sub-resource of `/routes`.
** The response SHALL include a `Preference-Applied: respond-async` header.
** The response body SHALL be a status document with at least the following properties:

*** `routeId`: a unique identifier for the route computation
*** `type`: SHALL be "route"
*** `status`: the current status of the computation (one of: "accepted", "running", "successful", "failed", "dismissed")

^|C |If the server does not support asynchronous execution for the requested mode:

** The server SHALL respond with status code `400 Bad Request`.
** The response body SHALL be a problem details document (RFC 9457) explaining that asynchronous execution is not supported.
|===

[[req_job-control_status]]
[width="90%",cols="2,6a"]
|===
^|*Requirement {counter:req-id}* |*/req/job-control/status*
^|A |The server SHALL support the HTTP GET operation at the path `/routes/{routeId}` to retrieve the status of a route computation.
^|B |The response to the request SHALL depend on the status of the computation:

** Calculation in progress (status is "accepted" or "running"): 200 OK with a status document (`application/json`).
** Calculation complete (status is "successful"): 200 OK with the route (`application/geo+json`).
** Route does not exist: 404 Not Found with problem details (RFC 9457).
** Valid request, but no route can be computed: 422 Unprocessable Entity with problem details (RFC 9457).
** Unexpected server failure: 500 Internal Server Error with problem details (RFC 9457).
|===

[[req_job-control_modes]]
